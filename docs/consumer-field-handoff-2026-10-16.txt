DECISION: Separate authentication from resource addressing.
API bearer credential authenticates a client to a tenant. A session ID selects a browser session under that authority. A page ID selects a tab owned by that session. These are NOT interchangeable. Current API code hashes bearer keys and maps their digests to tenants (packages/api/src/server.ts apiKeysFromEnv and bearer checks). That is tenant scope, not proof of a per-session scoped credential. Several clients may share a tenant; issue separate credentials when individual revocation/audit is needed.
IP address is a network attribute, not a client identity: NAT, proxies, shared hosts and multiple agents on loopback collapse many clients into one IP. Never replace credentials with an IP address or alias. Auth and operator approval remain distinct.

TOKEN LENGTH
8/12 hex characters encode only 32/48 random bits; 8/12 base64 characters at most 48/72 bits. Too weak as the recommended bearer-secret design, even when scope is narrow. UUIDv4 has 122 random bits; UUID versions are not interchangeable and its string is not especially token efficient. Prefer a CSPRNG-generated 32-byte bearer secret (43 unpadded base64url characters), or at least 16 random bytes (22 chars) if a reviewed design requires a smaller credential. Keep the existing strong key during active work; no rotation or restart requested here.
An independent 8–12 character NONSECRET credential ID is fine for display and lookup; require the full secret for authentication. Do not accept token prefixes. Separate random display IDs from secret material.
Reference: https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html recommends CSPRNG generation and at least 128-bit custom session credentials. This recommendation is for secret credentials, not ordinary resource IDs.

VERIFIED PAGE-ID REPRESENTATION
packages/engine-firefox/src/index.ts: FirefoxPage.id = `page-${randomUUID()}`.
packages/api/src/service.ts: create page and popup registration both use `pg_${++this.pageCounter}_${enginePage.id}` (popup uses popup.id).
Thus public IDs embed the adapter's internal page ID; Firefox exposes a verbose generated UUID, not demonstrated raw Mozilla browsing-context data. Chromium in this live run produced a short composite pg_<counter>_page-<counter>. Do not call the Firefox string a leaked secret or a confirmed security vulnerability.
packages/core/src/session-coordinator.ts generates ses_<Date.now()>_<Math.random base36 suffix>. Existing collision/pending allocation guards exist. These identifiers must never become bearer credentials: Math.random is not a cryptographic credential generator.

PROPOSED DESIGN — preserve protocol compatibility before changing canonical IDs
1. CLI/MCP client context stores endpoint, nonsecret credential profile name, session ID and page ID privately. Commands can use explicit context aliases, e.g. --context upwork --page p1 (PROPOSED syntax, not implemented). Resolve within the current authenticated tenant/session; no global mutable default or reliance on IP.
2. Keep secret outside model prompts/tool argv via existing AGENTBROWSER_API_KEY environment or a new --api-key-file option. Existing --operator-key-file is operator-only and must not be repurposed. CLI currently lists --api-key and env, no agent --api-key-file. Add bounded regular-file input, restrictive permissions, deterministic precedence and complete redaction; never echo the credential. MCP reloads its own environment; sourcing another terminal cannot update an existing process.
3. Return short nonsecret aliases such as s1/p1 in compact client mode. Store mapping to canonical opaque IDs locally; include server-instance generation/epoch internally so a restart cannot redirect an alias to a new page. No unsafe prefix matching. Unknown, expired or ambiguous mappings fail explicitly.
4. If canonical page IDs are changed later, allocate an engine-independent opaque ID in the service, map it to EnginePage internally, and do the same for popups. Prefer a checked 12-character random base64url ID or monotonic ID within a proven non-reused namespace; 8–12 chars are appropriate only for nonsecret addressing with collision checks. Keep tenant+session ownership checks for every operation. Never truncate UUIDs without collision handling.
5. Page/session IDs are not sufficient authorization, regardless of length. Keep revocation, session TTL, least privilege and independent human approval gates. A true session-scoped capability token, if introduced, is a separate secret and needs its own reviewed lifecycle; do not overload the public session ID.
